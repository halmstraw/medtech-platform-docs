Product Understanding · 1 of 2

The Problem Worth Solving

A cuffless, contactless blood pressure monitor. No hardware. Just a phone.

The science

  • rPPG captures micro colour changes in facial skin
  • Extracts blood volume pulse signal
  • Derives HR and blood pressure
  • ~1% colour change from ambient light

Where we are

  • CE Class IIa — EU MDR certified
  • Deployed in NHS primary care
  • FDA 510(k) / De Novo in progress
  • B2B SDK — embedded in partner clinical apps

The tension

  • Engineering wrapper must mature to FDA-submission standard
  • Small team, high regulatory bar
  • Scale economics need to improve
  • BP estimation: the hard frontier
Assumption: B2B SDK delivery model assumed. If the primary route is direct-to-clinician app, some mobile architecture framing shifts.

  • Target <1p per assessment

Theme A — Cloud Architecture · 1 of 3

Platform Foundation Principles

Decoupled, event-driven, and auditable by default

Immutable Infrastructure

  • Terraform IaC — nothing hand-configured in production
  • Every environment reproducible from source
  • Regulated environments cannot tolerate drift

Event-Driven Assessment Lifecycle

  • Assessment request as an event, not a synchronous call chain
  • Enables replay, retry, and audit natively
  • Decouples ingestion from inference latency

Audit Trail as Design Constraint

  • Not bolt-on logging — structured events at every boundary
  • The audit log is the compliance record
  • Required for IEC 62304 traceability

API Contract as First-Class Artefact

  • OpenAPI spec versioned alongside code
  • Breaking changes require an ADR before implementation
  • SDK stability is a commercial commitment
Trade-off: Event-driven adds operational complexity. I'd apply it to the assessment pipeline — where auditability is a regulatory requirement — not as a blanket pattern across every internal service.

Assessment Architecture: Current → Target

Assumed current — to be validated

  • New container per assessment, load-balanced
  • ~7p per assessment

Target state

Theme A — Cloud Architecture · 3 of 3

Service Boundaries: Where and Why Not

Decompose where it reduces regulatory blast radius — not for its own sake

ServiceResponsibilityWhy a boundary here?
signal-api Ingestion, validation, anonymisation PII boundary — raw video decisions isolated here
inference-service ML model invocation, versioned via MLflow Independent deployability for model updates
results-service BP/HR output, audit event emission Clinical output isolated for validation scope
identity-service SDK authentication, API key lifecycle Security boundary, independent rotation
What I'd keep coherent: inference-service internals. Splitting pre-processing, inference, and post-processing into separate services creates distributed complexity with no regulatory benefit.

Trade-off: Four services = four deployables to operate. I'd sequence their separation across phases — not land all four simultaneously.
Theme B — Engineering Governance · 1 of 3

Architecture Governance Model

Quality gates and decision records — the layer above delivery process. Sprint discipline and team shape sit with the Head of Engineering.

Architecture Decision Records (ADRs)

  • Written before implementation — not retrospectively
  • Format: context → decision → rationale → alternatives rejected
  • Stored in repo, reviewed via PR, immutable once merged
  • "Why did we choose this?" has a legal answer in a regulated context

CI-Enforced Quality Gates

  • Static analysis (SonarCloud)
  • Security gate (Snyk) — no critical vulnerabilities ship
  • SBOM generation (Syft) — FDA cybersecurity artefact, every build
  • Traceability gate — PR links to Issue with risk class before merge

Change control: Scope of change = scope of re-validation. Surgical changes reduce regulatory burden. Architecture-significant changes require an ADR before a PR is raised.

People and governance: Governance frameworks only work if the team believes in them. I invest in people understanding why a gate exists — not just that it does. Engineers who understand the regulatory consequence of a missing traceability link make better decisions than those following a checklist. That comes from coaching, not compliance.

Theme B — Engineering Governance · 2 of 3

Testing Strategy

Shaped by IEC 62304 software safety class

Layer 1 — Unit & Integration
  • GitHub Actions, pytest
  • Standard coverage gates
  • AI-assisted test generation welcome
  • AI-merged tests are not
  • Fast, automated, developer-owned
Layer 2 — System Verification
  • TestRail as test management
  • Requirement → test case → execution → result
  • Third-party tester submissions
  • IEC 62304 §5.7 artefact
  • Appears in regulatory submission
Layer 3 — Clinical Performance
  • Separate from software verification
  • Bland-Altman vs auscultatory reference
  • Fitzpatrick I–VI skin tone stratification
  • Longitudinal stability required
  • FDA De Novo submission artefact
Trade-off: The temptation is to let test evidence accumulate informally and back-fill before submission. The cost of back-filling is always higher than the cost of discipline. The compliance agent enforces traceability linkage at PR time — making drift visible before it becomes a problem.
Theme B — Engineering Governance · 3 of 3

CI/CD, Release Management & Instrumentation

Pipeline Gates

  • Build + unit tests
  • SonarCloud quality gate
  • Snyk dependency + container scan
  • SBOM generation (Syft) — every build
  • TestRail execution trigger
  • Human approval gate to production — always

Release Model

  • Every sprint → release candidate
  • Production: PO sign-off + QA gate + regulatory checklist
  • Immutable artefact registry (ACR)

Cloud Instrumentation

  • Grafana + Prometheus: infra & service metrics
  • Loki: structured log aggregation
  • Sentry: error tracking + release correlation
  • Key metrics: assessment success rate, inference latency p50/p95/p99, queue depth

Mobile Instrumentation

  • Signal quality: SNR per ROI, motion artefact rate, rejection rate
  • Outcome: HR/BP confidence scores, uncertainty bounds
  • Sentry mobile: crash rate, ANR rate, B2B SDK integration errors
  • Key metric: % assessments with signal sufficient for clinical output
Trade-off: Mobile telemetry must be privacy-preserving — signal quality metrics sent as aggregated numbers, not raw biometric values. Needs explicit definition in the data classification framework.
Theme C — Client-Side Performance · 1 of 2

Mobile Architecture

The SDK is the primary integration surface. Treat it like a product.

Architecture Patterns

  • MVVM + Clean Architecture — iOS (Swift/SwiftUI) and Android (Kotlin)
  • rPPG signal capture behind a platform-agnostic abstraction layer
  • Camera/spectrum pipeline swappable without touching business logic
  • Shared patterns across platforms, platform-native quality preserved

SDK as a Product

  • Semantic versioning with explicit deprecation policy
  • Compatibility matrix: SDK version × OS version × camera capability
  • B2B partner developer experience is a commercial concern
  • Partner onboarding documentation owned alongside the SDK
Assumption: Current iOS/Android codebase structure unknown — UIKit vs SwiftUI, shared abstractions vs parallel codebases. Architecture confirmed after onboarding audit on day one.
Theme C — Client-Side Performance · 2 of 2

On-Device Compute: What's Realistic

Signal extraction on-device. BP inference in the cloud. For now.

Runs on-device (target)

  • Face detection + landmarks: MediaPipe — production-proven
  • ROI extraction: forehead + left and right cheeks
  • POS + CHROM extraction, SNR-weighted fusion
  • Signal quality scoring — reject low-SNR before transmission
  • Anonymisation — raw RGB never leaves the device

Stays in the cloud (for now)

  • BP estimation model — complex, updated frequently
  • MLflow model registry — versioned deployments
  • Easier to audit and version-control centrally
  • FDA controlled release evidence maintained cloud-side
GPU acceleration: Metal (iOS) · Vulkan (Android)  |  ME-rPPG (2025): 3.6 MB, 9.46 ms latency — on-device DL benchmark  |  Pruning + quantisation: up to 46× size reduction
Trade-off: On-device extraction reduces cost, improves privacy, enables offline operation. Trade-off: mobile CI/CD complexity and validation across a fragmented device/OS matrix. Phase 2 priority, not day one.

Measuring Whether It's Delivering Value

Instrument the tooling. Don't fly blind on AI ROI.

PR cycle time (open → merge)
Baseline before rollout, tracked weekly after. The headline productivity signal.
Review comment action rate
% of AI-generated comments resulting in a code change. Proxy for signal quality.
Traceability coverage at PR time
% of PRs with complete requirement → test linkage before merge. Compliance agent contribution.
False positive rate
High false positives → noise → engineers route around agents. Monitor and tune continuously.
Engineer satisfaction (quarterly)
Lightweight survey. Are people using the tooling, or working around it?
Governance
All prompts version-controlled. LLM tooling: data residency compliant, no training on proprietary code. Quarterly review cycle.
Trade-off: Agents add latency to the PR cycle. Prompt quality and tuning is an ongoing investment — not a one-time setup cost. Budget for it explicitly.

Forward Look · 2 of 3

Three Investments Worth Making

Beyond the blueprint — where I'd place longer bets

Long game

On-Device BP Inference

  • Literature is pre-clinical on calibration-free BP
  • Architecture should be ready when science catches up
  • Build on-device/cloud abstraction now — model location swappable later
  • ME-rPPG shows <10ms on-device inference achievable
Competitive moat

Proprietary Clinical Dataset

  • No public dataset sufficient for clinical-grade BP across diverse populations
  • Best public benchmark (MMPD): only 33 subjects
  • Diverse, longitudinal, smartphone-captured dataset
  • A differentiator no competitor can quickly replicate
Data leverage

Self-Supervised Pre-Training

  • Contrastive learning on unlabelled facial video
  • Bootstraps models before fine-tuning on scarce labelled BP data
  • Doesn't require expensive label collection to start
  • Likely necessary step toward clinical-grade BP accuracy

02
ADRs 001–007 — remaining architectural decisions documented before more code is written. Decisions before content, every time.

Understand the team — where people are, where they want to go, and what's getting in their way. The architecture only executes if the people delivering it are growing and motivated.

One honest uncertainty: BP estimation from rPPG is not a solved problem. DBP approaches clinical thresholds in controlled conditions; SBP does not. Most defensible near-term position: HR regulated to clinical grade, BP advisory with confidence bounds — with a credible path to clinical-grade BP as the evidence base grows.
